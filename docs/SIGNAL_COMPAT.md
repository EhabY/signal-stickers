# Signal Compatibility

Everything this tool depends on that Signal controls. Signal's server API is private and can change
without notice; when something breaks, start here.

Re-check each item against the reference files in
[Signal-Desktop](https://github.com/signalapp/Signal-Desktop) (paths below are relative to that
repo). Last verified against Signal-Desktop `8.34.0-alpha.1` on 2026-10-17.

Last confirmed end to end against Signal production on 2026-10-17: linking a device (QR scan,
`PUT /v1/devices/link`), pushing a pack (upload form and S3 upload), and pulling it back with
byte-identical images. If something breaks after that date, Signal changed it.

## Hosts

- **Ours:** `packages/core/src/env.ts`
- **Signal:** `config/production.json` and `config/default.json` (`serverUrl`, `cdn.0`)
- Chat service: production `https://chat.signal.org`, staging `https://chat.staging.signal.org`.
- CDN: production `https://cdn.signal.org`, staging `https://cdn-staging.signal.org`.

## Pinned CA

- **Ours:** `packages/core/src/net/signalCa.ts`, generated by `scripts/sync-signal-ca.ts`
- **Signal:** `config/default.json` → `certificateAuthority` (production inherits it)
- The current CA expires on 2032-01-24. To update:
  `node scripts/sync-signal-ca.ts <path to Signal-Desktop>`, then run the tests.

## CDN paths

- **Ours:** `packages/core/src/net/cdn.ts`
- **Signal:** `ts/textsecure/WebAPI.preload.ts` → `getStickerPackManifest`, `getSticker`
- Manifest `GET {cdn}/stickers/{packId}/manifest.proto`, sticker
  `GET {cdn}/stickers/{packId}/full/{stickerId}`. No authentication.

## Request headers

- **Ours:** `packages/core/src/net/cdn.ts` and `packages/core/src/net/chat.ts`
  (`User-Agent: signal-stickers`), `packages/core/src/account/credentials.ts` (`getChatAuth`)
- **Signal:** `ts/textsecure/WebAPI.preload.ts` (`_ajax`, `getFetchOptions`),
  `ts/util/getUserAgent.node.ts`
- We identify as `signal-stickers` instead of copying Signal-Desktop's user agent, and send no
  `X-Signal-Agent`. If the servers start rejecting unknown agents, this is the place.
- Chat requests use `Authorization: Basic base64(username:password)` with username `aci.deviceId`,
  or the bare aci for `PUT /v1/devices/link`.

## Pack crypto

- **Ours:** `packages/core/src/stickers/crypto.ts`
- **Signal:** `ts/Crypto.node.ts` (`deriveStickerPackKey`, `decryptAttachmentV1`),
  `sticker-creator/src/util/crypto.ts`
- HKDF-SHA256 over the 32-byte pack key, 32 zero bytes of salt, info `"Sticker Pack"`, 64 bytes out:
  AES key then MAC key. Blobs are `iv(16) || AES-256-CBC || HMAC-SHA256(iv || ciphertext)`.
- The known-answer tests in `packages/core/test/stickers/crypto.test.ts` pin these constants.

## Manifest proto

- **Ours:** `packages/core/src/protocol/protobuf.ts` (`decodeStickerPack`)
- **Signal:** `protos/Stickers.proto`
- `title = 1`, `author = 2`, `cover = 3`, `stickers = 4`; each sticker `id = 1`, `emoji = 2`.
  Unknown fields are skipped, so additions are harmless; renumbering is not. Like Signal's decoder
  (`ts/protobuf/compiled.std.js`, `@indutny/protopiler`), a repeated `cover` replaces the earlier
  one and strings keep a leading U+FEFF.

## Pull semantics

- **Ours:** `packages/core/src/stickers/pull.ts`
- **Signal:** `ts/types/Stickers.preload.ts` (`fetchStickerPackContents`,
  `parseStickerPackManifest`)
- Stickers without an id are skipped. A missing cover falls back to the first sticker; a cover id
  outside the list is downloaded separately. Readers accept up to 1024 stickers.

## Link format

- **Ours:** `packages/core/src/stickers/link.ts`
- **Signal:** `ts/util/signalRoutes.std.ts` (`artAddStickersRoute`), `ts/util/Stickers.std.ts`
- `https://signal.art/addstickers/#pack_id=<32 hex>&pack_key=<64 hex>` and
  `sgnl://addstickers?pack_id=…&pack_key=…`. Pack ids are redacted as `[REDACTED]` plus the last
  three characters, like Signal does.

## Image formats

- **Ours:** `packages/core/src/stickers/image.ts`
- **Signal:** `sticker-creator/src/constants.ts`, `ts/util/sniffImageMimeType.std.ts`
- Stickers are PNG/APNG or WebP. Anything else is saved as `.bin` so it is visible rather than
  mislabelled.

## Provisioning socket

- **Ours:** `packages/core/src/account/provisioningTransport.ts`
- **Signal:** `ts/textsecure/Provisioner.preload.ts`, `ts/textsecure/SocketManager.preload.ts`
  (`connectProvisioning`)
- libsignal's `Net.connectProvisioning` with user agent `signal-stickers` and
  `Environment.Production` or `Staging`. `@signalapp/libsignal-client` is pinned to the exact
  version in Signal-Desktop's `package.json`; update the two together.

## QR code

- **Ours:** `packages/core/src/account/scan.ts`
- **Signal:** `ts/textsecure/Provisioner.preload.ts`, `ts/util/signalRoutes.std.ts`
  (`linkDeviceRoute`)
- `sgnl://linkdevice?uuid=<address>&pub_key=<base64 public key>&capabilities=nopni%2Cnopni2`, built
  with `URLSearchParams` like Signal-Desktop.
- A new code every 45 s with the previous one still scannable (two sockets at most), 6 codes in all,
  and 10 s for each socket to connect and receive its address (`ROTATION_INTERVAL`,
  `MAX_OPEN_SOCKETS`, `MAX_ROTATIONS`, `QR_CODE_TIMEOUTS`). Unlike Signal-Desktop, a socket that
  fails to connect fails the link instead of retrying with backoff.

## Provisioning cipher and message

- **Ours:** `packages/core/src/account/provisioningCipher.ts`,
  `packages/core/src/protocol/provisioning.ts`
- **Signal:** `ts/textsecure/ProvisioningCipher.node.ts`, `ts/Crypto.node.ts` (`deriveSecrets`,
  `verifyHmacSha256`), `ts/textsecure/Provisioner.preload.ts` (`prepareLinkData`),
  `protos/DeviceMessages.proto`
- Version byte 1. HKDF-SHA256 over the X25519 shared secret, 32 zero bytes of salt, info
  `"TextSecure Provisioning Message"`, 96 bytes out: cipher key, then MAC key. The body is
  `version || iv(16) || AES-256-CBC || HMAC-SHA256` over everything before the MAC.
- `ProvisionEnvelope`: `publicKey = 1`, `body = 2`. `ProvisionMessage` fields we read:
  `aciIdentityKeyPrivate = 2`, `number = 3`, `provisioningCode = 4`, `aci = 8`, `pni = 10`,
  `pniIdentityKeyPrivate = 12`, `aciBinary = 17`, `pniBinary = 18`.
- The aci comes from `aciBinary` or the lowercased `aci`; a pni needs its identity key and the
  number. Signal-Desktop also requires the profile key, master key or account entropy pool, and auth
  credential salt; we never read messages or profiles, so we do not.
- The known-answer tests in `packages/core/test/account/provisioningCipher.test.ts` were computed
  with `node:crypto` only.

## Device link request

- **Ours:** `packages/core/src/account/register.ts`, `packages/core/src/account/keys.ts`
- **Signal:** `ts/textsecure/WebAPI.preload.ts` (`linkDevice`, `linkDeviceResultZod`,
  `serializeSignedPreKey`), `ts/util/getCapabilities.std.ts`, `ts/Crypto.node.ts`
  (`generateRegistrationId`), `ts/Curve.node.ts` (`generateSignedPreKey`, `generateKyberPreKey`),
  `ts/textsecure/AccountManager.preload.ts` (`createAccount`)
- `PUT /v1/devices/link` with Basic auth `aci:password`, where the password is base64 of 16 random
  bytes without its last 2 characters. The body, in Signal-Desktop's order: `verificationCode`,
  `accountAttributes` (`fetchesMessages: true`, `name`, `registrationId`, `pniRegistrationId` when
  the phone shares its number, `capabilities`), `aciSignedPreKey`, `aciPqLastResortPreKey`, and the
  PNI prekeys when there is a number. The reply is `{ uuid, pni?, deviceId }`.
- As in `createAccount`, the reply's `uuid` must be the ACI the phone provisioned, and its `pni`,
  when present, the PNI the phone provisioned (the reply's is untagged). Otherwise Signal has
  already added the device, so linking fails and tells the user to remove `signal-stickers` on the
  phone before linking again.
- `fetchesMessages` must be `true`: Signal-Server's
  `LinkDeviceRequest.isExactlyOneMessageDeliveryChannel` accepts a device only if it fetches
  messages or has exactly one APNs/FCM push token, and answers 422 otherwise (confirmed against
  production on 2026-10-17). Any other 422 means the body no longer passes the server's validation:
  compare it with `LinkDeviceRequest` and `DeviceAttributes`.
- Capabilities copy `getCapabilities`: `attachmentBackfill`, `spqr`, `usernameChangeSyncMessage`,
  and `optionalPhoneNumber` when there is no number. A 409 usually means the server now requires a
  new capability: copy it from there.
- Registration ids are 1 to 16383. Each identity gets a signed EC prekey (33-byte key) and a signed
  last-resort Kyber prekey (1569-byte key) with random 24-bit ids, sent as base64
  `{ keyId, publicKey, signature }`.
- Errors follow `ts/state/ducks/installer.preload.ts` (`finishInstall`) and
  `ts/textsecure/Utils.dom.ts` (`translateError`): 403 expired code, 409 outdated client, 411 too
  many devices, 413 and 429 rate limited.

## Device name

- **Ours:** `packages/core/src/account/deviceName.ts`
- **Signal:** `ts/Crypto.node.ts` and `ts/textsecure/AccountManager.preload.ts`
  (`encryptDeviceName`), `protos/DeviceName.proto`
- X25519 of an ephemeral key and the ACI identity key gives the secret. The synthetic IV is the
  first 16 bytes of `HMAC(HMAC(secret, "auth"), name)`, the key is
  `HMAC(HMAC(secret, "cipher"), syntheticIv)`, and the cipher is AES-256-CTR from a zero counter.
  `DeviceName`: `ephemeralPublic = 1`, `syntheticIv = 2`, `ciphertext = 3`, sent as base64. The name
  is always `signal-stickers`.

## Unlink

- **Ours:** `packages/core/src/account/link.ts` (`unlinkDevice`)
- **Signal:** `ts/textsecure/WebAPI.preload.ts` (`unlink`)
- `DELETE /v1/devices/{deviceId}` as `aci.deviceId`. A 401 or 403 counts as already unlinked,
  because the phone may have removed the device first.

## Linking instructions

- **Ours:** `packages/cli/src/account.ts` (`SCAN_INSTRUCTIONS`, and the advice when saving fails),
  `packages/web/src/components/AccountView.svelte`
- **Signal:** `_locales/en/messages.json` (`icu:Install__scan-this-code`,
  `icu:Install__instructions__1` to `__3`)
- We tell users to scan in Settings > Linked devices > Link new device, and to remove
  `signal-stickers` there when linking half-fails. If the phone app renames these screens, update
  the wording.

## Upload form

- **Ours:** `packages/core/src/stickers/push.ts`
- **Signal:** `ts/textsecure/WebAPI.preload.ts` (`StickerPackUploadFormSchema`, `putStickers`)
- `GET /v1/sticker/pack/form/{count}` on the chat service as the linked device, where `count` is the
  number of images including a separate cover. The reply is `{ packId, manifest, stickers }`, each
  slot `{ key, credential, acl, algorithm, date, policy, signature }`. Slots pair with images by
  position, as in `putStickers`; their `id` is not read.

## S3 upload

- **Ours:** `packages/core/src/net/cdn.ts` (`upload`)
- **Signal:** `ts/textsecure/WebAPI.preload.ts` (`makePutParams`, `putStickers`)
- `POST {cdn}/` with `multipart/form-data` and a boundary of 16 dashes and 32 hex characters. The
  fields, in order: `key`, `x-amz-credential`, `acl`, `x-amz-algorithm`, `x-amz-date`, `policy`,
  `x-amz-signature`, `Content-Type: application/octet-stream`, then the `file` part. The policy
  fields are the only authentication.
- The manifest goes first, then the images three at a time. Signal-Desktop sets no per-request
  timeout; we allow 120 s per upload.

## Pushed manifest

- **Ours:** `packages/core/src/stickers/encryptPack.ts`
- **Signal:** `sticker-creator/src/util/crypto.ts` (`encrypt`),
  `sticker-creator/src/selectors/art.ts` (`selectUrl`)
- A fresh random 32-byte pack key. Sticker ids are 0 to n-1 in pack order, with their emoji. The
  cover reuses the first sticker with identical bytes, or else is an extra image with id
  `stickers.length` and no emoji. Unlike the sticker creator, identical sticker images are uploaded
  once per sticker, so ids always match the uploads.

## Sticker limits

- **Ours:** `packages/core/src/stickers/validate.ts` (`STICKER_LIMITS`, `validatePack`)
- **Signal:** `sticker-creator/src/constants.ts`, `sticker-creator/src/selectors/art.ts`,
  `sticker-creator/src/util/processImage.ts`, `sticker-creator/src/util/apng.ts`
- 1 to 200 stickers of at most 300 KiB (300 × 1024 bytes) each. A title, an author, a cover, and an
  emoji per sticker are required. Readers accept more stickers; see
  [Pull semantics](#pull-semantics).
- The creator uploads an APNG unchanged, so it must be square, 10x10 to 512x512, and loop forever
  (`num_plays` 0). Any other image becomes a 512x512 WebP, so we require PNG and WebP to be 512x512.
- Our own rule, not Signal's: no two stickers may share an image, by bytes or by file name, though
  the cover may reuse one. The creator's `encrypt` (`sticker-creator/src/util/crypto.ts`) uploads a
  repeated image once but numbers stickers by position, so its manifest can name images it never
  uploaded.
